# Go版本

## 写法1\-分点叙述

**智能OnCall Agent系统**

**项目介绍： **智能OnCall系统通过AI Agent解决团队真实痛点，整合 **知识库、对话、运维 **三大核心能力，实现 **问题自动应答 **和 **故障智能排查 **的一体化服务。致力于降低团队OnCall的人力成本，提升团队效率。

**技术栈 **：Goframe、Eino、RAG、ReAct、Plan\-Executor、Multi\-Agent、MCP

**个人职责：**

•

**负责 AI Agent 架构设计 **：基于 Eino 框架设计并实现了多个AI Agent，包括 **Knowledge Index Agent、Chat ReAct Agent和 Plan\-Execute\-Replan Agent**

•**负责 RAG 知识库系统设计 **：设计了完整的 **文档向量化存储和检索方案 **，支持内部文档的智能检索增强生成。使 AI 能够基于内部知识库 **提供准确的业务咨询和技术支持 **。

•**负责对话功能开发：基于 ReAct 模式实现了对话Agent 。 **实现业务咨询、告警自救、工单预处理等场景无缝切换，一次开发覆盖研发、运维、业务方多角色需求。

•**负责AIOps功能开发 **：基于 **Plan\-Execute 模式 **实现了 **智能运维Agent，解决了传统运维需要人工排障的低效问题，将运维响应时间从小时级降低到分钟级。**

**项目亮点：**

•**AI Agent 架构设计： **通过图编排实现模块化的 Agent 工作流。 **设计并实现了多通用工具集 **，包括通过 **MCP 协议集成日志查询 **工具、 **Prometheus 告警查询工具、MySQL 数据操作工具、联网查询 **等，使 AI Agent 能够灵活调用外部工具完成复杂任务。

•**RAG 知识库系统设计： **在 RAG 系统中，需要 **处理文档分块大小和检索TopK参数 **的选择。分块过小会丢失上下文，过大会降低检索精度；TopK 过大会影响性能，过小可能遗漏关键信息。经过测试验证，确定了最优参数组合，知识检索准确率达到 85%\+

•**对话功能 **：支持 **多轮对话上下文记忆 **，并通过容错处理优化体验。同时基于 **SSE技术实现AI对话流式输出 **，解决大模型响应延迟问题，前端呈现实时对话效果。

•**AIOps功能： **实现了 **根据告警信息 → 检索知识库 → 规划执行步骤 → 调用工具查询 → 分析结果 → 生成建议 **的完整业务流程。能够自动根据内部文档查询监控信息和日志信息，通过工具调用实现自动化监控告警查询和日志分析，并结合历史工单生成运维建议方案。

# PDF 文档解析与 OCR：面试问答（规划能力）

> 本节用于回答“下一步如何扩展 RAG 文档解析”的设计题，**不是当前项目已经上线的能力**。当前源码中上传接口只接受 `.txt`、`.md`，并以 UTF-8 文本读取；没有 PDF、OCR、PaddleOCR、Docling 或云文档解析服务的依赖与调用链。面试时不能把以下方案写成已完成项目成果。

## 1. 当前项目的文档解析链路是什么？

当前的 RAG 写入链路是：

```text
POST /api/upload
  → 校验扩展名（txt / md）与 10 MB 大小
  → 保存至 uploads/
  → 以 UTF-8 读取文件全文
  → 按 Markdown 或普通文本切分
  → 生成 Embedding
  → 将 Chunk、向量和来源元数据写入 Milvus
```

`.md` 会先按一级、二级标题切分，再按字符长度二次切分并合并过小片段；`.txt` 直接使用递归字符切分。每个 Chunk 保存 `_source`、`_extension`、`_file_name`，Markdown 还可保留 `h1`、`h2` 标题信息。当前二次切分目标约为 1600 字符（配置 `chunk_max_size=800` 的两倍），重叠为 100 字符。

回答时要强调：这是一条**文本入库**链路，不是通用文档解析平台；当前不支持 PDF、Word、Excel、PPT、HTML、图片或扫描件 OCR。

## 2. 为什么 PDF 不能只用一个“转文本”库解决？

PDF 是容器格式，至少应区分：

- 原生文本 PDF：由 Word、网页或系统导出，页面中有可复制的文本层；
- 扫描 PDF：每页本质是图片，没有可用文本层；
- 混合 PDF：同一文件中同时存在原生文本页和扫描页；
- 复杂版式 PDF：双栏、跨页表格、图文混排、表单或大量页眉页脚。

直接提取原生文本对扫描件无效；对所有文件强制 OCR 又会增加延迟和成本，并可能降低原生文本的准确性。因此主流做法是“**原生文本优先，按页 OCR 回退，复杂版式再启用布局与表格解析**”。

## 3. 推荐的 PDF 解析架构是什么？

```text
PDF 上传
  → 校验真实 MIME / %PDF- 文件头、大小、页数、加密状态和处理配额
  → 按页提取原生文本、文本块和坐标（PyMuPDF）
  → 判断文本层质量
      ├─ 质量合格：保留原生文本块
      └─ 空白、乱码或疑似扫描页：渲染页面并调用 OCR
  → 对双栏、表格、图文混排文档执行版面/表格解析（可选 Docling）
  → 清理重复页眉、页脚、水印与空白元素
  → 按标题、段落、表格边界切 Chunk
  → 写入 Milvus，并保留页码、章节和解析来源元数据
```

建议将解析与索引拆开：上传接口只保存并创建索引任务，后台任务执行 PDF 解析、OCR、向量化和写入。对用户真实返回 `uploaded`、`indexing`、`indexed`、`failed` 等状态，不能因文件落盘成功就宣称知识库更新成功。

## 4. PaddleOCR 是否适合作为本项目的 OCR 选择？

**适合，且对于中文或中英混合企业资料，应优先作为 OCR 后端候选。** 它适合离线/本地部署，能够避免将内部 PDF 直接发送到第三方云服务，并对扫描件、截图型页面和中文内容有良好的适配空间。

但 PaddleOCR 只负责“从图像识别文字”，不等于完整 PDF 解析。因此不能把所有 PDF 直接丢给 OCR。推荐的职责划分是：

```text
原生文本 PDF       → PyMuPDF 直接提取（快、文字更准确）
扫描或文本层失效页 → PaddleOCR（识别中文/中英文字）
复杂表格和多栏页   → Docling 等布局/表格层 + OCR 后端
```

Tesseract、RapidOCR、EasyOCR 和云端文档智能服务也都是可选项。PaddleOCR 的优势并不意味着其他方案没有价值：例如外部云服务可能在票据、表单或特定表格任务上更省开发工作，但会引入费用、网络依赖、数据合规和供应商锁定问题。

## 5. 为什么还需要 Docling 或版面分析？

只把每一页 OCR 成一大段文本，会丢失标题层级、表格行列关系、双栏阅读顺序和图注归属，进而产生错误 Chunk 与错误检索结果。

布局解析层负责区分标题、段落、列表、表格、图片、页眉和页脚；表格应作为独立内容单元输出，而不是和前后段落拼接。Docling 可以作为复杂文档的增强解析器：它负责文档布局、表格结构与结构化输出，OCR 引擎只作为它的文字识别后端之一。

## 6. PDF 入库后的 Chunk 与引用应如何设计？

不要先把整份 PDF 压成纯文本再按固定字符数切分。应优先按“章节 → 段落/列表 → 表格”组织，过长元素再二次切分，并保存可追溯元数据：

```json
{
  "_source": "/uploads/oncall-runbook.pdf",
  "_file_name": "oncall-runbook.pdf",
  "_extension": ".pdf",
  "_page_start": 12,
  "_page_end": 12,
  "_section_path": ["告警处理", "磁盘空间告警"],
  "_content_type": "paragraph",
  "_parser": "pymupdf",
  "_ocr_used": false
}
```

若来自 OCR，还应保存 OCR 置信度、页面坐标和语言信息。这样最终回答可引用“文件名、第 12 页、磁盘空间告警章节”，也可以在低置信度时提示用户核验原文。

## 7. 这个改造的关键工程风险有哪些？

- 仅按 `.pdf` 后缀校验不可靠，应校验 MIME、文件头和真实解析结果；
- 要限制文件大小、页数、渲染像素、总字符数、OCR 超时和并发数，防止资源耗尽；
- 加密、损坏或无密码可读的 PDF 必须返回明确失败原因，不能伪装成“空知识”；
- 应在新版本完整解析和向量写入成功后，再切换/删除旧版本 Chunk，避免索引失败导致旧知识消失；
- 原始 PDF、OCR 文本和图片均是不可信输入，不应无限制写日志或直接注入模型；
- 需要用真实但脱敏的 PDF 评测集验证：原生文本、中文扫描件、双栏、跨页表格、图文混排和代码块；评测重点是页码引用、召回与答案依据，不只是“能否抽出文字”。

## 8. 一分钟面试回答示例

> 当前项目的 RAG 入库只支持 UTF-8 的 Markdown 和 TXT，Markdown 会按标题和长度切分后向量化，因此没有把 PDF OCR 写成既有能力。若要扩展，我会设计成原生文本优先、按页 OCR 回退的异步解析链路：先用 PyMuPDF 提取文本块、页码和坐标；没有可靠文本层的扫描页再使用 PaddleOCR。对于双栏和表格密集文档，再引入 Docling 做布局和表格结构识别。最终按章节、段落和表格切 Chunk，并将页码、章节路径、坐标、OCR 置信度写入 Milvus 元数据，保证检索结果可以追溯到具体页。工程上还会增加文件真实性、页数与超时限制、后台索引状态，以及新索引成功后再替换旧向量的机制。
