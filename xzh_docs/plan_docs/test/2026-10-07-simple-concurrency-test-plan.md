# 多智能体平台简易阶梯并发测试方案

> 日期：2026-10-07
>
> 状态：待执行；本文不包含实测结果，也不代表已通过任何并发档位。
>
> 适用分支：`multi-agents`
>
> 目标：用可复现的小规模测试验证并发行为，形成能够支撑面试追问的真实记录。

## 1. 测试范围

采用 Python `asyncio + HTTPX` 编写测试脚本，通过统一 SSE 接口模拟多个请求同时运行。
不搭建完整压测平台，不在本阶段开展生产级容量认证、长期稳定性测试或完整故障注入。

重点回答以下问题：

- 并发提升后，任务完成率和响应时间如何变化？
- 知识查询、数据查询与复杂任务的表现有什么差异？
- 不同请求的事件、运行结果和线程是否串线？
- 失败来自应用、数据库、MCP，还是模型服务配额？

这里的“并发数”指同时在途的 Agent 请求数量，不等同于在线用户数量。
每个请求可能产生多次 LLM、Embedding 和工具调用。

## 2. 环境与准备

使用真实 FastAPI、PostgreSQL、Milvus、模型与 Embedding 服务，以及配置好的 MCP 服务。
知识库提前完成索引，测试过程中不同时上传或重建索引。
若 MCP 示例服务使用模拟数据，报告注明“真实模型与协议、示例业务数据”，不要描述为
生产数据源压测。

固定并记录以下条件：

| 项目 | 待填写内容 |
|---|---|
| 代码基线 | 分支、commit、未提交改动说明 |
| 服务配置 | 机器 CPU/内存、Worker 数、是否经过代理 |
| 模型 | 模型名称、超时、重试配置 |
| 配额 | 已知 RPM、TPM、并发限制；未知则标注未知 |
| 数据 | 文档数量、Chunk 数量、MCP 数据来源 |
| 持久化 | PostgreSQL、连接池上限、工作记忆是否启用 |
| 发压环境 | 本机或独立机器、HTTPX 连接池与超时 |
| 执行边界 | 总请求数、最大测试时长、调用预算 |

凭据通过运行环境注入，不将 Key、Token、真实 `.env` 或敏感业务内容写入文档和结果文件。
如果发压端与服务端共用电脑，应注明资源竞争会影响结论。

认证启用时，提前准备测试账户和 Token，不将每次登录混入任务性能测试；刷新 Token 的
时间也不计入 Agent 请求耗时。只使用测试线程，保留本次创建的线程 ID 以便后续定向清理。

## 3. 请求场景

准备三组小型样本池，每组至少 3 条。先单请求确认它们在当前知识库和工具配置下可执行。

| 场景 | 样本要求 | 检查重点 |
|---|---|---|
| 知识查询 | 查询已导入文档中的制度、FAQ 或 SOP | 检索、回答、来源引用 |
| 数据查询 | 查询存在的测试工单、告警或指标 | 工具调用、动态证据、错误披露 |
| 复杂任务 | 先查询数据，再结合已有 SOP 分析并给出建议 | 依赖步骤、知识与数据协作 |

示例问题需替换为测试环境真实存在的文档、服务或工单标识，避免把“查不到数据”误判为
并发故障。复杂任务只查询和分析，不要求修改系统或执行处置操作。

混合负载建议比例为知识 40%、数据 40%、复杂任务 20%。1 并发时分别测三类场景；
10/30/50/100 并发时按上述比例分配，例如 50 请求中知识 20、数据 20、复杂任务 10。
路由由 Supervisor 实际决定，记录 `route_decided` 的模式和目标，不把预期场景当成实际路径。

每个请求使用独立的新线程。本方案验证跨线程并发，不验证同线程同时写工作记忆的冲突，
也不以单账户多线程测试宣称已完成跨用户权限隔离验证。

## 4. 并发档位与执行顺序

| 阶段 | 并发数 | 执行方式 |
|---|---:|---|
| 冒烟及基线 | 1 | 三类场景逐个执行，每类至少 3 次 |
| 普通负载 | 10、30 | 每档先执行一批混合请求 |
| 较高负载 | 50 | 前一档结果可接受时继续 |
| 压力探索 | 100 | 前一档稳定且预算允许时执行 |

每批包含目标档位数量的请求，完成后不自动补充新的请求。这是一批并发验证，
不是持续保持固定并发的容量压测。

默认将同批请求在约 3 秒内均匀启动，记录真实的最大在途请求数；部分任务提前完成时，
实际峰值可能低于目标值，必须如实报告。所有任务结束后等待约 30 秒，再开始下一批。
首批无明显异常、预算可控时，每档最多重复三批。

可选：在已经稳定的档位额外执行一批同时启动的请求，验证突发流量。结果单独标记，
不与渐进启动的数据混合。

出现持续模型限流、明显超时增长、数据库连接池错误或预算达到上限时，不继续升档。
记录触发条件，待在途任务结束、资源恢复后再分析。100 并发是探索目标，不是验收承诺。

## 5. 脚本最小实现要求

本方案仅定义脚本要求，尚未实现发压脚本。后续建议放在独立测试工具目录，支持
`base_url`、并发数、批次数、启动窗口、超时、样本文件和结果路径等参数。

请求顺序：

```text
准备认证信息
  -> POST /api/agent/threads 为每个请求创建独立线程
  -> 按本批计划启动 POST /api/agent/run_stream
  -> 完整消费 SSE，校验事件和终态
  -> 写入逐请求测量记录
  -> 批次结束后抽查 GET /api/agent/runs/{run_id} 和 Trace
```

线程预创建耗时不计入 Agent 耗时。请求体使用当前公开契约：

```json
{
  "thread_id": "服务端返回的线程ID",
  "message": "样本池中的问题"
}
```

HTTPX 客户端复用连接，连接池容量应容纳目标并发及少量余量，避免客户端默认配置造成
本地排队。记录连接池等待或 `PoolTimeout`，不能将其直接归因于服务端。
客户端使用单调时钟计时，明确区分连接超时、无数据读取超时和整个任务截止时间。
总截止时间根据复杂任务基线设置，例如初始候选值 300 秒；不要直接将 LLM 单次调用的
60 秒超时当成整个复杂任务的上限，也不要无限等待。

SSE 解析按空行切分完整事件，合并同事件的 `data:` 行后解析 JSON，忽略心跳和注释。
收到 HTTP 200 仅代表连接成功，必须持续读取到终态并正常结束事件流。

## 6. 成功判定和指标

对每个请求记录以下时间点：

- 发出 Agent 请求的时间。
- 收到 `run_started` 的时间。
- 收到首个非空 `content_delta` 的时间。
- 收到终态事件的时间。

首答案耗时从请求发出算至首个非空答案片段；失败且没有答案时填写空值，不能记为零。
完整任务耗时算至终态；没有终态的超时或断流请求记录已等待时间和失败分类，但不混入
正常完成任务的耗时分位数。HTTP 成功率与业务完成率分别统计。

当前正常终态的业务结果位于 `event.data.result`。`run_completed` 可能承载 `partial`，
因此不能只根据事件名认定业务成功。异常路径的 `run_failed` 可能只有错误摘要、没有
`data.result`；脚本须兼容并判为失败。

最小校验：

1. 正常完整消费的事件流恰好包含一个终态：`run_completed` 或 `run_failed`。
2. 同一流的 `run_id`、`thread_id` 一致，线程 ID 与请求匹配。
3. 每个事件 ID 唯一；不同独立请求的 Run ID 不重复。
4. 终态结果非空，按实际状态分别统计 `completed`、`partial`、`failed`。
5. 知识和复杂场景抽查回答、来源及子目标覆盖，防止“执行完成但内容不正确”。
6. 每批抽查少量完成 Run 的查询和 Trace，确认持久化可读取、ID 与响应对应。

ID 一致性只能证明基础隔离行为，不能单独证明答案没有混入其他请求内容；内容需要抽查。
正常完整流的校验不适用于主动断连实验；本方案不将主动断连混入主测试。

逐请求记录建议包含：

```text
batch_id / scenario_id / sample_id / target_concurrency
request_id / thread_id / run_id / actual_route
http_status / business_status / error_category
first_event_ms / first_content_ms / terminal_ms / elapsed_ms
terminal_count / event_count / identity_check_passed
```

错误分类至少区分 HTTP 错误、客户端超时或断流、业务 partial/failed、模型限流、
MCP 失败和数据库失败。服务端没有披露具体原因时填写“未知”，不要凭耗时猜测。

## 7. 一个模型 Key 的处理方式

一个 Key 可以进行并发测试。它用于认证，实际容量取决于服务商对账号、项目、模型的
RPM、TPM 和并发限制。多个同账号 Key 可能共享配额，不以轮换 Key 绕过限制。

知识查询通常包含 Supervisor、Knowledge 回答和最终生成等多次调用；复杂任务还涉及
Planner、步骤路由、Replanner 和可能的 Reviewer。Embedding 也有自己的配额。
因此 50 个用户请求不等于 50 次模型调用。

执行前记录已知配额和预算，从低档位升高。执行期间观察限流响应、超时和重试，
能获取服务商错误码时进行脱敏记录。重试配置保持固定，报告说明重试可能增加耗时与调用量。

若高档位主要因模型配额失败，报告为“当前模型配额下的端到端容量限制”，不能声称
FastAPI 本身已达到极限。若需要定位应用容量，可另做可控模型替身对照；替身结果独立
报告，不替代真实模型测试。

## 8. 简易观察与结果表

不要求部署完整监控平台。每档记录服务 CPU、内存和明显日志异常；资源观察写明
采样方式。检查模型限流、MCP 超时、数据库连接等待和工作记忆更新警告。
现有 Metrics 的成本字段可能为空，费用以服务商账单或实际计量为准。

汇总表按每档整体记录，必要时另按场景细分：

| 目标并发 | 实际峰值 | 请求数 | completed | partial | failed/超时/断流 | 首答案均值 | 完成耗时均值/P95 | 主要异常 |
|---:|---:|---:|---:|---:|---:|---|---|---|
| 1 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 |
| 10 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 |
| 30 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 |
| 50 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 |
| 100 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 |

业务完成率 = `completed` 请求数 / 全部已提交 Agent 请求数。partial 单独列出，
HTTP 错误、超时和断流也计入总分母。P95 写明样本量和计算口径，小样本只作初步观察；
即使失败样本不进入完成耗时统计，也必须在同表披露，避免因慢请求失败导致指标表面改善。

合格底线是没有重复终态、ID 串线等协议错误。延迟和业务完成率目标在执行前结合
单请求基线设定，当前不虚构统一性能门槛。该测试不证明长期稳定性或生产最大容量。

## 10. 对应源码与交付物

当前方案基于以下接口和契约：

- `app/api/agent.py`：线程创建、SSE、Run 和 Trace 查询。
- `app/models/agent.py`：请求体、事件信封和业务状态。
- `app/services/multi_agent_service.py`：终态生成、持久化和工作记忆更新。
- `app/config.py`：模型、工具、数据库和运行限制。

执行后的最小交付物为：发压脚本、脱敏样本集、逐请求 CSV/JSONL、结果汇总与环境说明。
结果文件遵循仓库生成文件忽略规则。正式报告可按仓库文档约定放入
`xzh_docs/eval_reports/`，明确标注并发测试的范围与条件。
