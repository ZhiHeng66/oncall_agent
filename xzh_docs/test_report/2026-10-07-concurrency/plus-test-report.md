# Qwen Plus 真实阶梯并发测试报告

日期：2026-10-07。状态：全部计划批次已执行，存在业务异常，不是全部用例验收通过。

## 结论

全部角色使用 `qwen-plus` 非思考模式，真实调用模型、Embedding、Milvus、PostgreSQL
及本地 MCP 服务。9 条串行基线和 10/30/50/100 四个并发档位各三轮，共 579 条请求。
结果为 565 completed、13 partial、1 failed，completed 比例 97.58%。

579 条请求均为 HTTP 200，均收到唯一 SSE 终态，run/thread/event ID 检查通过。
**HTTP 200、协议通过、completed 均不等同于回答正确。**

本次证明在此环境及样本下，应用能够处理峰值 100 个在途请求并返回明确终态；
不能据此宣称生产环境持续支持 100 用户、完整语义准确率 97.58%，或没有性能问题。

## 配置与执行方式

- 分支 `multi-agents`，工作区包含已有未提交修改；提交号不代表完整被测源码快照。
- 为避免使用 9900 上的旧进程，在 9901 启动当前工作区的独立 Uvicorn 测试实例，单 Worker。
- 启动进程明确覆盖 `DASHSCOPE_MODEL`、`RAG_MODEL`、`SUPERVISOR_MODEL`、
  `SPECIALIST_MODEL`、`REVIEWER_MODEL` 为 `qwen-plus`，`LLM_ENABLE_THINKING=false`。
  脚本 results.json 的 model_configuration 表示发压客户端本身不检查服务器配置；
  本报告的型号来自此次启动时明确传入的参数，不是从真实 `.env` 读取所得。
- 沿用应用已有凭据加载机制，没有读取、打印或修改真实 `.env`。
- Embedding 保持 `text-embedding-v4`，不重建知识库。既有集合 `biz` 有 26 条向量 entity，
  不是 26 份文档；使用仓库公开业务文档和示例工单。
- 本机 macOS arm64，10 个逻辑 CPU、24 GiB 内存；发压客户端与服务同机。
- 保留真实认证，新建一个普通权限测试账号，每批重新登录刷新 Token，每请求创建新线程。
- 混合负载为 40% 知识、40% 工单数据、20% 复杂任务，每类有三个公开样本。
- 每批在 3 秒内逐步发出请求，批间暂停 30 秒。这是突发阶梯测试，不是恒定并发长时间稳态测试。
- 单请求客户端总时限 300 秒，最多 579 条请求，总执行时限 7200 秒。
- 协议或持久化抽查失败即停；单批非 completed/partial 达到 20%，或至少两条被分类为模型限流时停止。
  partial 单独记录。本次未触发停止条件。

执行命令：

```bash
.venv/bin/python tools/run_local_load_test.py \
  --base-url http://127.0.0.1:9901 \
  --output xzh_docs/test_report/2026-10-07-concurrency/plus-run-01 \
  --levels 10 30 50 100 --repeats 3 --window 3 --pause 30 \
  --timeout 300 --max-requests 579 --max-duration 7200
```

## 路由与内容核对

按原始场景分组：知识 231 completed；数据 227 completed / 3 partial / 1 failed；
复杂任务 107 completed / 10 partial。

基线中知识请求三条均进入 Knowledge，工单请求三条均进入 Data，三条复杂请求均 completed。
工单基线的编号、状态及一次工具调用匹配，复杂基线有知识和 MCP 两类来源。

全量公开 Run 内容做关键词与来源核对，不保存完整答案：

- 231 条工单请求全部首次进入 Data；229 条答案包含预期编号与状态，2 条未通过该检查，
  分别是 partial 和 failed。没有发现另一测试工单编号串入答案。
- 知识请求首次路由 229 次 Knowledge、2 次 Task；两次 Task 是额外编排，不应称为全部路由最优。
- 交付约束关键词 76/76、SLA 时间关键词 73/73、FAQ 关键词 82/82 通过。
  这些检查不验证每个语句的事实、否定关系或引用与结论是否严格对应。
- 117 条复杂请求均出现预期工单编号，114 条同时有知识与 MCP 来源，3 条缺少完整来源且均为 partial。
- 复杂请求首次路由 63 次 Task、54 次 parallel。样本含“先查询、再检索/分析”，
  因此仍需检查模型是否把真正有依赖的任务误当成独立并行查询；不能以 completed 掩盖这一点。
- 在有限的关键词/来源检查中，completed 请求没有发现上述检查失败；这不是完整语义验收，
  也不是跨用户隔离测试或准确率评估。

## 异常及优化方向

1. 9 条请求公开 errors 含“没有可用于该任务的只读数据工具。”，其中 8 partial、1 failed。
   failed 位于 `mixed-100-2-18`，termination_reason 为 `all_specialists_failed`。
   这表示 Agent 没有完成数据任务，但不能仅凭文本断定是模型生成空计划、权限筛选、工具发现，
   或并发缓存问题。后续应按对应 Run/Trace 复核工具计划、白名单筛选和 Provider 健康状态，
   增加不泄露参数的结构化失败原因。
2. 13 partial 中 10 条 termination_reason 为 `review_limit`，3 条为 `review_passed` 但仍保留错误。
   有限返工及失败终态机制确实被实际触发；更换 Plus 没有消除所有业务失败。
   后续可检查定向返工是否补齐缺失证据，以及修复后旧错误的状态语义和最终披露规则。
3. 真正有步骤依赖的任务仍可能被并行路由。应优先补充路由回归样本和确定性约束，
   对数据任务未调用工具、复杂任务缺少双来源等结果级信号触发复核；本次没有实现这些修改。
4. 100 档位出现明显等待增长，下一步可在相同样本上增加节点/工具/连接池等待分段观测，
   再决定是否增加模型调用并发上限、背压或 Worker；不要直接认定增加 Worker 就能解决。

错误分类中没有记录到欠费、模型认证、模型限流、数据库或客户端超时类失败。
该结论只限本次可见的公开错误分类；没有获得完整供应商日志，不能证明底层没有重试或瞬态错误。

## Flash 与 Plus 对照的边界

Flash 运行按用户要求中断，保留 [flash-run-01/report.md](flash-run-01/report.md)
和 [flash-summary.json](flash-summary.json)。原始 stop_reason 仍为 running，是旧版脚本
中断时未改写该字段；它不是仍在后台发压。账号已禁用，Flash 实例已停止。
已保存 69 条结束请求，未完整执行全部档位，中断中的请求不用于性能结论。

相同九条基线中，Flash 的三条工单请求均走 Knowledge、未返回预期工单状态，
三条复杂请求均 partial；Plus 三条工单均走 Data，九条基线全部 completed。
这支持“本样本下 Plus 更适合当前配置”的有限结论，不是受控大样本模型能力评测。
两种模型仍使用相同路由策略，Plus 也有残余路由问题，不能认为换型号替代了纠错机制。
